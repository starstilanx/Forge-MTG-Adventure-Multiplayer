# Adventure Multiplayer Update
**Date**: May 31, 2026

## Overview
This update fixes the bug where only the host received rewards after a co-op combat encounter. The client would always return to the world map empty-handed because the client-side reward generation in the `BATTLE_END` handler was incomplete: it only ran when `battleEnemy.rewards != null` and only incremented the win counter if rewards were non-empty. Enemies without an explicit `rewards` array (chaos battles, sprite-level dialog rewards, or enemies whose `RewardData.generate()` returned empty given a null card pool) caused the client to silently skip all rewards.

## Root Cause

### Host reward path (always worked)
1. `DuelScene.GameEnd()` → `afterGameEnd()` → broadcasts `BATTLE_END`, then transitions back to the previous scene
2. `Forge.switchToLast()` returns `TileMapScene` or `GameScene` (both extend `HudScene implements IAfterMatch`)
3. `HudScene.setWinner()` → `MapStage.setWinner()` or `WorldStage.setWinner()`
4. Calls `currentMob.getRewards()` → `EnemySprite.getRewards()`, which handles chaos battles, sprite-level extra rewards, and enemy-deck card pulls
5. Shows `RewardScene`

### Client reward path (broken)
```java
// Old BATTLE_END handler — three ways to silently skip rewards:
if (humanWon) {
    final EnemyData battleEnemy = DuelScene.instance().getNetworkEnemyData();
    if (battleEnemy != null && battleEnemy.rewards != null) {  // fails if rewards field is null
        for (final RewardData rdata : battleEnemy.rewards) {
            rewards.addAll(rdata.generate(false, null, true));  // null card pool → no card rewards
        }
        if (!rewards.isEmpty()) {           // only increments win counter if rewards non-empty
            Current.player().win();
            DuelScene.instance().setPendingClientRewards(rewards);
        }
    }
}
```

Problems:
1. `battleEnemy.rewards != null` — skips if enemy has no explicit reward table (chaos mode, enemies using only sprite-level rewards)
2. `rdata.generate(false, null, true)` — passing `null` for the card pool means "random card from enemy deck" rewards generate nothing; host uses the actual deck list
3. `Current.player().win()` only called when rewards non-empty — win counter always wrong when #1 or #2 fires

## Fix

### Approach: Host generates rewards once, serializes them into the `BATTLE_END` payload

The host already runs `EnemySprite.getRewards()` (the full reward logic) as part of `MapStage.setWinner()` → `getReward()`. We call it a second time in `afterGameEnd()` to produce the client's reward set (independently randomized), serialize each `Reward` to a compact string, and include the strings in the `BATTLE_END` payload. The client simply deserializes and displays them — no need to replicate `EnemySprite.getRewards()` logic client-side.

**Reward serialization format** (each reward is one `String` in the payload):
| Format | Meaning |
|---|---|
| `Gold:N` | N gold pieces |
| `Life:N` | Heal N life |
| `Shards:N` | N mana shards |
| `Card:name` | Named card (sellable) |
| `CardNoSell:name` | Named card (no-sell) |
| `Item:name` | Named item |

**BATTLE_END payload** changed from `Boolean humansWon` to `String[]`:
- `[0]` = `"true"` or `"false"` (winner)
- `[1..]` = zero or more serialized reward strings (absent if no rewards or on loss)

A `Boolean` payload is still accepted in the `BATTLE_END` handler as a legacy fallback.
